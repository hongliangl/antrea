# OVS Pipeline Snapshots

The `.txt` files in this directory record every OpenFlow flow, group and meter that the Antrea
Agent installs on a Linux K8s Node for a set of configurations and a fixed set of objects. They
are generated from the code in `pkg/agent/openflow` without a cluster and without OVS, and they are
checked by the unit tests. A change that modifies any flow must update these files, so reviewers
see the flow change as a diff.

The files are generated by `TestPipelineSnapshots` in
[pipeline_snapshot_test.go](../../../../pkg/agent/openflow/pipeline_snapshot_test.go). The test
builds the OpenFlow client with the fake client of the unit tests, calls the same client methods
the Agent calls at startup and for each object, and records the result in place of OVS.

## Regenerating

After changing flows, run the following command and commit the result:

```bash
make pipeline-snapshots
```

It runs the test with `UPDATE_PIPELINE_SNAPSHOTS=1`, which rewrites the files. Without the variable
the test compares the code with the files and fails at the first differing line. This check runs
with the other unit tests of `pkg/agent/openflow`.

## Configurations

All configurations are a Linux K8s Node with IPv4 only, and the file name is
`<mode>-<configuration>.txt`.

| Configuration | Features | Modes |
|---|---|---|
| `default` | AntreaProxy, AntreaPolicy and Egress, the defaults of the fake client | `encap`, `noencap`, `hybrid` |
| `proxy-all` | `default` plus `proxyAll` | `encap` |
| `l7-network-policy` | `default` plus L7NetworkPolicy | `encap` |
| `traffic-control` | `default` plus TrafficControl | `encap` |
| `multicast` | `default` plus Multicast | `encap` |
| `egress-traffic-shaping` | `default` plus EgressTrafficShaping | `encap` |
| `dsr` | `default` plus `proxyAll` and LoadBalancerModeDSR | `encap` |
| `all` | every feature above together | `encap`, `noencap`, `hybrid` |

The files for a single feature exist only for `encap`, because the flows of those features do not
depend on the traffic mode, while the PodConnectivity and Egress flows do and are covered by
`default` and `all` in every mode.

OVS meters are on in every configuration. Every snapshot is a Linux Node, and OVS supports meters on
Linux. Only Windows lacks them. With meters, the NetworkPolicy packet-in flows use the packet-in
meters 256, 257 and 258.

`egress-traffic-shaping` differs from `default` only in the shaping flows and the Egress meter. The
Egress mark flows go to the `EgressQoS` table, which exists only with shaping, so the IDs of the
tables after it are one higher.

Every configuration could be generated, and all the features listed can be enabled together.
Multi-cluster, AntreaIPAM (uplink connected to the bridge), IPsec, WireGuard, IPv6 and Windows are
not covered yet.

## Mock Objects

The objects are the same in every configuration. An object that needs a disabled feature is not
installed. The `Objects` line in the header of each file lists what was installed.

The local Node `node-a` is the fake client of the unit tests:

| Item | Value |
|---|---|
| Node IP | 192.168.77.100/24 |
| Pod CIDR | 10.10.0.0/24 |
| Gateway | 10.10.0.1, MAC 0a:00:00:00:00:01, OF port 32769 |
| Tunnel | OF port 32768 when the mode or Egress needs one |
| Service CIDR | 10.96.0.0/16 |
| Egress except CIDR | 192.168.78.0/24 |
| L7 NetworkPolicy ports | target 300, return 301 |

The fake client puts the L7 NetworkPolicy ports on OF ports 10 and 11, which are the ports of the
Pods below, so the test moves them to 300 and 301.

The Egress except CIDR is a fixture of the fake client and happens to be the subnet of `node-c`.

| Object | Source label | Details |
|---|---|---|
| Node `node-b` | `node:node-b` | Node IP 192.168.77.101, same subnet as `node-a`, Pod CIDR 10.10.1.0/24 |
| Node `node-c` | `node:node-c` | Node IP 192.168.78.101, another subnet, Pod CIDR 10.10.2.0/24 |
| Pod `client` | `pod:client` | 10.10.0.10, MAC 0a:58:0a:0a:00:0a, OF port 10 |

| Endpoint `db` | `endpoint:10.10.1.11:80` | remote Endpoint of `svc-web`, on `node-b` |
| Service `svc-web` | `service:svc-web` | ClusterIP 10.96.0.10, TCP port 80, cluster group only |

| L7 NetworkPolicy rule | `policy:allow-client-to-web-http` | same rule with HTTP `GET /` and VLAN ID 1 |
| Egress | `egress:egress-client` | `client` with local SNAT IP 192.168.77.200 and mark 1 |
| TrafficControl mirror | `tc:mirror-web` | `web` in both directions to OF port 200 |

| Multicast group | `multicast:224.1.1.1` | `web` as the only local receiver |

The following labels are for calls the Agent makes once and not for an object:

- `init` is for the default flows of every table and for the initial flows, groups and meters of
  every feature, installed when the Agent connects to OVS.
- `agent:egress` is for the flows that skip SNAT for the Service CIDR.
- `agent:l7-network-policy` is for the flows that send traffic to and from the L7 engine.
- `agent:multicast` is for the IGMP query group of all local Pods and, when the mode supports
  encap, the group that reports to `node-b` and `node-c`.

The objects are installed in the way the Agent installs them:

- Node flows are installed with the Node transport IP. The client decides between tunnel and
  routing with `NeedsTunnelToPeer`, so in `hybrid` mode `node-b` is routed and `node-c` is
  tunneled.
- The Service follows the proxier. Endpoint flows come first, then the cluster group with both
  Endpoints, then the ClusterIP flows. With `proxyAll`, it also installs NodePort 30080 on the
  virtual NodePort DNAT IP 169.254.0.252 and the LoadBalancer IP 192.168.77.150. With DSR, the
  LoadBalancer IP uses DSR. The Endpoints are installed one at a time only to label each flow with
  its Endpoint.
- Group IDs come from the group allocator of the client, as in the Agent, so the NetworkPolicy
  groups take the first IDs.
- The NetworkPolicy rule uses rule ID 1 and OpenFlow priority 44900. The L7 rule uses rule ID 2 and
  priority 44899. The priorities are fixed values, not the output of the priority assigner.
- With EgressTrafficShaping, the Egress also has a 10000 kbps meter with a burst of 20000.

## File Format

A file starts with a header of lines beginning with `#`. It gives the configuration, the traffic
mode, the features that the client was built with, and the objects installed, in order.

Then there is one section per table, in pipeline order, which is also the order of table IDs:

```text
[ARPSpoofGuard] table 1
PodConnectivity | pod:client | priority=200,arp,in_port=10,arp_spa=10.10.0.10,... actions=goto_table:ARPResponder
```

Each line is `<feature> | <source> | <flow>`:

- `<feature>` is the category encoded in the flow cookie, such as `PodConnectivity`,
  `NetworkPolicy`, `Service`, `Egress` or `Multicast`. The table miss flows generated for every
  table are in the `Default` category. TrafficControl flows are in the `PodConnectivity` category
  and L7 NetworkPolicy flows in the `NetworkPolicy` category, because that is how the code sets
  their cookies.
- `<source>` is the label of the call that installed the flow, as described above. A flow installed
  by more than one object lists all of them, separated by commas.
- `<flow>` is the flow without its cookie and table.

In a table, flows are sorted by priority, highest first, then by text. The file ends with a
`[groups]` section sorted by group ID and a `[meters]` section sorted by meter ID, both as
`<source> | <entry>`.

**Note**: The flows are rendered by the `binding` library of Antrea, the same code the unit tests
use to print flows, and not by `ovs-ofctl dump-flows`. The two differ in several ways. Tables
always appear by name, for example `goto_table:ConntrackZone`, where `ovs-ofctl` shows table
numbers unless it is given `--names`. Ports always appear by number, for example `in_port=32769`,
where `ovs-ofctl --names` shows `in_port="antrea-gw0"`. Some fields keep an explicit bit range, for
example `OXM_OF_VLAN_VID[0..11]` where `ovs-ofctl` shows `OXM_OF_VLAN_VID[]`. Flow statistics are
not shown. Use these files to review what the code installs, not to compare with a dump from a
Node character for character.
